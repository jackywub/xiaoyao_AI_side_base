# 成长工作台手机端 App PRD

> 版本：v0.1  
> 日期：2026-07-26  
> 状态：初稿  
> 基于范围：当前 `my_website2` 中的成长工作台实现、数据模型和 API 能力

## 1. 产品概述

成长工作台手机端 App 是现有 Web 端成长工作台的移动化版本，目标不是把桌面页面原样搬到手机里，而是把“每天打开后知道做什么、快速记录做了什么、晚上完成复盘、持续推进项目和副业收益”的核心链路做成更轻、更快、更适合随手使用的个人行动系统。

当前 Web 端已经具备较完整的私有工作台底座：

- 登录后访问 `/workspace`，工作台不被搜索引擎索引。
- 数据已从浏览器 LocalStorage 迁移到 MySQL，前端通过 `/api/workspace` 读取和写入。
- 已有模块包括数据看板、任务管理、项目推进、目标设定、副业收益、成长记录、网站内容、AI 助手和设置。
- 手机端已有底部导航雏形：数据看板、任务管理、项目推进、成长记录为主入口，其他入口收进“更多”。
- 成长记录已覆盖阅读、运动、学习、灵感、复盘，并接入微信读书同步和 Obsidian 复盘保存。
- AI 助手已接 Hermes，能够读取任务、项目、习惯摘要，用于计划、拆解和复盘。

手机端 App 的第一版应聚焦高频个人使用场景：今日行动、任务打勾、快速记录、每日复盘、项目推进和 AI 辅助。

## 2. 产品定位

### 2.1 一句话定位

一个为个人副业和成长节奏服务的手机行动工作台。

### 2.2 目标用户

首要用户是当前工作台所有者，即个人创作者/咨询服务经营者“萧小遥”：

- 每天需要管理内容、副业项目、咨询服务、学习输入和个人成长。
- 希望把任务、收益、阅读、运动、灵感和复盘放在同一个系统里。
- 经常在手机上临时记录想法、完成任务、查看今日进展。

后续可扩展到同类型用户：

- 个人品牌经营者。
- AI 副业实践者。
- 内容创作者、咨询顾问、知识服务者。
- 希望用目标、任务、复盘闭环管理自己的人。

### 2.3 用户核心问题

1. 今天要先做什么不够清楚。
2. 桌面工作台信息完整，但手机上使用成本偏高。
3. 灵感、运动、阅读、复盘等记录发生在碎片时间，需要更快入口。
4. 项目推进和副业收益之间有关联，但手机端缺少一个轻量查看方式。
5. AI 助手已有能力，但需要更贴近移动端的快捷提问和上下文入口。

## 3. 产品目标

### 3.1 V1 目标

- 用户每天可以在 30 秒内看清今日重点任务和完成状态。
- 用户可以在 10 秒内完成任务打勾、成长记录或灵感捕获。
- 用户可以在睡前完成一份结构化复盘，并自动带入当天任务完成情况。
- 用户可以查看项目阶段、风险和下一步，并用手机添加推进记录。
- 用户可以基于当前工作台数据向 AI 助手提问。

### 3.2 衡量指标

| 指标 | V1 目标 |
|---|---|
| 日活使用 | 每日至少打开 1 次 |
| 今日任务完成操作时长 | 打开 App 后 30 秒内可完成第一个打勾 |
| 快速记录完成时长 | 从首页入口到保存成功不超过 10 秒 |
| 每日复盘完成率 | 每周至少 5 天完成复盘 |
| 数据保存成功率 | 核心写入接口成功率高于 99% |
| AI 助手可用率 | Hermes 可连接时请求成功率高于 95% |

| 网站内容 | 管理页面、文章、项目、服务和案例 | 不进入手机 App MVP，仅保留 Web 管理 |

### 4.2 当前技术与数据基础

- 前端：Next.js App Router、React、TypeScript、Tailwind CSS。
- 数据库：MySQL + Prisma。
- 认证：管理员登录、数据库会话、HttpOnly Cookie。
- 主接口：`GET /api/workspace`、`POST /api/workspace`。
- 外部接口：`/api/workspace/weread`、`/api/workspace/assistant`、`/api/settings`。
- 数据边界：一个用户对应一个 Workspace，所有私有数据通过 Workspace 归属。
- 历史迁移：浏览器 LocalStorage 可一次性导入 MySQL。

### 4.3 当前不足

- 现有页面仍偏桌面表单，手机端输入路径较重。
- 底部导航只是响应式适配，不是完整 App 信息架构。
- 暂无推送提醒、离线草稿、桌面小组件、分享扩展等移动端能力。
- 习惯和时间块已有数据模型或组件痕迹，但不是当前导航主流程。
- 网站内容管理不适合作为手机 App 的 MVP 核心。

## 5. MVP 范围

### 5.1 V1 必须包含

1. 登录与会话保持。
2. 今日首页：今日任务、完成率、关键成长统计、快捷记录入口。
3. 任务管理：今日任务、四象限、每日/阶段/长期任务、子任务、快捷打勾。
4. 成长记录：阅读、运动、学习、灵感、复盘的新增、查看和编辑。
5. 每日复盘：自动生成当日任务摘要，用户填写收获不足和明日计划，保存到 MySQL，并在配置后同步 Obsidian。
6. 项目推进：项目列表、阶段进度、风险、下一步行动、推进日志。
7. AI 助手：快捷提问、手动提问、读取当前工作台上下文。
8. 更多入口：目标、收益、阅读书架、设置。
9. 数据同步：复用当前 MySQL 主存储，Web 和 App 数据一致。

### 5.2 V1 暂不包含

- 网站内容管理。
- 支付、会员、多用户协作。
- 复杂日程编排和完整日历系统。
- App Store/应用市场完整上架流程中的商业化功能。
- 自动从健康 App 同步运动数据。
- 完整离线编辑冲突解决。

### 5.3 V1.1 可考虑

- 推送提醒：每日复盘、重点任务、目标行动。
- 离线草稿：无网时先保存本地，恢复网络后同步。
- 手机桌面小组件：今日完成率、下一项任务、复盘入口。
- 分享扩展：从微信、浏览器、读书 App 分享文字到灵感记录。
- 习惯入口：每日阅读、运动、学习、复盘的独立打卡视图。
- 时间块：把 `WorkspaceScheduleBlock` 做成移动端“今日安排”。

## 6. 信息架构

### 6.1 推荐底部导航

| Tab | 名称 | 说明 |
|---|---|---|
| 1 | 今日 | 今日概览、关键任务、快捷记录、复盘提醒 |
| 2 | 任务 | 任务列表、四象限、子任务、阶段/长期任务 |
| 3 | 项目 | 项目阶段、风险、下一步、推进日志 |
| 4 | 成长 | 阅读、运动、学习、灵感、复盘记录 |
| 5 | AI | 计划拆解、项目分析、复盘建议 |

目标、收益、阅读书架和设置从个人头像或“更多”面板进入。网站内容管理不进入 App 导航。

### 6.2 首页结构

今日首页从上到下建议为：

1. 顶部日期和问候。
2. 今日完成率、重点任务数、今日成长记录数。
3. “下一步行动”卡片：优先展示重要且未完成任务。
4. 今日任务列表：支持直接打勾。
5. 快捷记录区：阅读、运动、学习、灵感、复盘。
6. 项目下一步：展示 1 到 3 个项目的下一步行动和风险。
7. 收益简报：本月收入、支出、净收益。

## 7. 核心用户流程

### 7.1 早上计划

1. 用户打开 App，进入“今日”。
2. 系统展示今日任务、完成率和重点任务。
3. 用户点击“AI 排优先级”。
4. AI 基于未完成任务和项目下一步给出今日建议。
5. 用户将建议中的动作加入任务或子任务。

### 7.2 白天执行

1. 用户在今日列表中完成任务打勾。
2. 如果任务有子任务，点击展开后完成子任务。
3. 任务完成状态即时保存到 MySQL。
4. 首页完成率和项目关联状态刷新。

### 7.3 快速记录

1. 用户点击底部中间或首页的“+”按钮。
2. 选择阅读、运动、学习、灵感或收入。
3. 输入最少字段后保存。
4. 保存成功后更新今日记录和月度统计。

### 7.4 晚上复盘

1. 用户点击“写复盘”。
2. 系统自动汇总当日任务数、完成数、未完成项和完成率。
3. 用户填写“今日收获与不足”和“明天计划”。
4. 保存到 MySQL。
5. 若 Obsidian 已配置，同步写入 Obsidian 复盘目录。

### 7.5 项目推进

1. 用户进入“项目”。
2. 查看项目卡片上的阶段、进度、风险和下一步。
3. 点击项目进入阶段详情。
4. 添加推进记录，填写本次推进、进度和新的下一步。
5. 项目卡片进度和风险状态更新。

## 9. 交互与体验要求

### 9.1 移动端体验原则

1. 优先完成动作，再展示复杂管理。
2. 常用输入使用底部弹窗或抽屉，不跳转多层页面。
3. 列表默认短、清晰、可打勾；复杂字段折叠到详情。
4. 任何保存动作都必须有明确的成功、失败和保存中状态。
5. 首屏不堆满图表，图表只服务于判断。
6. 所有按钮和输入控件应适合单手触达。

### 9.2 关键组件

- 底部导航。
- 首页快捷记录按钮。
- 任务完成勾选控件。
- 日期切换器。
- 底部抽屉表单。
- 项目卡片。
- 阶段进度滑块或步进器。
- AI 聊天气泡和快捷提问按钮。
- 保存状态 Toast。

## 10. 数据与接口要求

### 10.1 数据复用策略

V1 应复用当前 MySQL 数据模型，不新建一套移动端数据表。手机端只改变交互层和部分 API 形态。

核心数据对象：

- `WorkspaceTask`：任务、子任务、目标。
- `WorkspaceTaskRecord`：每日任务执行记录。
- `WorkspaceGoalStage`、`WorkspaceGoalDailyAction`：目标阶段与每日行动。
- `WorkspaceProject`、`WorkspaceProjectStage`、`WorkspaceProjectProgressLog`：项目推进。
- `WorkspaceTransaction`：副业收支。
- `ReadingBook`、`ReadingDailyStat`：微信读书数据。
- `ExerciseRecord`、`LearningSession`、`Inspiration`、`DailyReview`：成长记录。
- `ExternalConnection`：外部连接。
- `AiConversation`、`AiMessage`：AI 对话。

### 10.2 API 策略

短期可以继续使用：

- `GET /api/workspace`
- `POST /api/workspace`
- `GET/POST /api/workspace/weread`
- `GET/POST /api/workspace/assistant`
- `GET/POST /api/settings`

App 化后建议逐步拆分为更清晰的移动端接口：

- `GET /api/mobile/home`
- `GET /api/mobile/tasks?date=YYYY-MM-DD`
- `POST /api/mobile/tasks/:id/toggle`
- `POST /api/mobile/quick-capture`
- `POST /api/mobile/review`
- `GET /api/mobile/projects`
- `POST /api/mobile/projects/:id/logs`

拆分的目的不是改变数据模型，而是减少手机端请求体复杂度和页面首次加载数据量。

### 10.3 同步策略

V1：在线优先。

- 所有写入实时提交服务端。
- 保存中禁止重复提交。
- 保存失败时保留用户输入。

V1.1：离线草稿。

- 快速记录、灵感、复盘可以先写本地草稿。
- 网络恢复后提示用户同步。
- 冲突处理以服务器最新数据为准，用户草稿作为待合并内容展示。

### 10.4 认证策略

如果 V1 采用 PWA 或移动 Web：

- 继续复用现有 HttpOnly Cookie 会话。

如果 V1 采用原生 App：

- 需要新增移动端安全会话方案，例如设备级 Refresh Token。
- Token 只存系统安全存储，不放普通 LocalStorage。
- 所有移动端 API 必须继续通过服务端解析用户身份，不信任客户端传入 `workspaceId`。

## 11. 技术形态建议

### 11.1 推荐路径

第一阶段建议做移动端 Web/PWA：

- 复用当前 Next.js、React 和 API。
- 最快验证手机端信息架构和高频流程。
- 可以添加到手机桌面，接近 App 使用方式。

第二阶段再根据使用频率决定是否封装原生 App：

- 可选 Capacitor：复用 Web 代码，补充推送、分享扩展等能力。
- 可选 Expo/React Native：体验更原生，但需要重写较多 UI。

### 11.2 V1 技术重点

- 重构工作台移动端布局，不只是响应式缩放。
- 首页接口轻量化，避免一次加载过多低频数据。
- 统一保存状态和错误提示。
- 针对触屏优化日期选择、任务打勾、快捷记录和底部抽屉。
- 保持 Web 端和手机端数据一致。

## 13. 风险与依赖

| 风险 | 影响 | 建议 |
|---|---|---|
| 当前工作台 API 使用单一 action 接口，手机端请求较重 | 首页加载和表单提交不够轻 | 逐步拆分移动端专用接口 |
| Hermes 依赖本机 CLI | 原生 App 或远程访问时 AI 不稳定 | 明确 AI 服务部署形态，或提供不可用降级 |
| Obsidian 同步依赖本地目录 | 手机上无法直接写本机目录 | PWA 阶段保留服务端写入；原生阶段重新设计同步方案 |
| 网站内容管理范围过大 | MVP 变成移动 CMS | 明确排除网站内容管理 |
| 原生 App 会话不同于 Web Cookie | 认证安全复杂度增加 | V1 先做 PWA，验证后再做原生 token |
| 图表和表单过多 | 手机端操作成本高 | 首页只展示关键判断，复杂分析保留 Web |

## 14. 待确认问题

1. 第一版是否接受先做 PWA，而不是直接上架原生 App？
2. AI 助手在手机端是否要作为底部主 Tab，还是先放在首页卡片和“更多”里？
3. 收益账本在手机端是否只做快速记账，复杂图表继续留在 Web？
4. Obsidian 同步在手机 App 场景下，是继续由服务器写本机目录，还是改成导出/复制/第三方同步？
5. 后续是否要开放给其他用户使用？如果要开放，需要补充多用户注册、权限、订阅和数据隔离策略。

## 15. 结论

成长工作台已经具备做手机端 App 的核心数据和业务底座。第一版不应追求“大而全”，而应把现有工作台里最高频的五个动作做顺：

1. 看今天要做什么。
2. 完成任务并打勾。
3. 随手记录阅读、运动、学习和灵感。
4. 晚上完成复盘。
5. 推进项目并让 AI 帮忙拆解下一步。

建议先用 PWA 方式完成 V1，复用当前 Next.js 与 MySQL 能力，在真实日常使用中验证移动端信息架构。等使用频率和关键流程稳定后，再决定是否封装原生 App。
